## Platform behaviour learned in the live runs

- **Scale-in needs `allowDataLoss: true`** on the infrastructure deploy; with `false` the deploy is refused at validation ("data loss will occur for products: Instance with ID …") and no task runs. `mc-edit.sh` takes `ALLOW_DATA_LOSS=1`.
- **A PATCH of the instance config while the previous deploy is still finishing returns HTTP 400.** `mc-edit.sh` now waits for `deployStatus != ongoing`.
- **Bundles are cached by URL.** Replacing a zip under the same name never reaches tasks, not even a manual retry of the failed job. Every bundle change needs a new zip name and a new extension; an existing instance cannot move to it.
- **A failed onEdit preDeploy blocks the deploy** (auto-retried 5×, then `thrown_error`). Skipping it lets the platform go on and remove the scale-in servers without the preDeploy work: for a CP scale-in that loses etcd quorum. Only skip it when the infrastructure is about to be deleted.
- **On a count decrease the platform removed the newest instances** (E6/E7: the last worker; C2 down: the two CPs added last). The leaver is known right after the PATCH (`GET /server-instances/<id>` → `config.deployType = delete`), before the deploy starts.
- **A removed instance's IP is reused** by the next new instance on the same network (instance-1110 got the address of the worker removed one edit earlier).
- **Virtual-media OS install on the R440s is fragile.** Server 12: no one-time CD boot was set, so it booted an old ESXi from disk (fixed with a Redfish one-time `Cd` boot + restart). Server 15 (BIOS 2.4.8): no usable disk boot entry after the install, so it booted the ISO again and reinstalled every ~11 min (fixed by booting from local disk by hand). Cause (seen on servers 3 and 15): the platform's `server_set_preferred_boot_order` puts the iDRAC virtual optical drive first (BIOS `SetBootOrderEn` = `Optical.iDRACVirtual.1-1,NonRAID…`); the installer reboots before `bootGeneratedOSImageFromVirtualMedia` notices the install has finished, so the server boots the ISO again and `configureBootFromBlockDeviceFirst` (which sets a continuous `Hdd` override) never runs. Servers that install cleanly reach that step in time. Moving the virtual drive last by hand does not last (the platform sets the order again on the next deploy; on these iDRACs the BIOS job either did not change the order or failed). Workaround: a one-time `Hdd` boot override while the last install pass runs.
